    Terms¶

    Software, coding, and SDLC vocabulary with abbreviations expanded, grouped by domain. Each term links to the section of this handbook that defines or discusses it. Terms the handbook doesn't cover yet link to an external reference, marked ↗.

    Domains: SDLC & Process · Management & Work Items · Requirements & Design · Coding · Version Control & Review · Testing & QA · System Design · Backend · Frontend · Networking · DevOps & SRE · Security, Privacy & Compliance · Data Engineering · Data Analysis · AI & LLM

    SDLC & Process¶

    Term Meaning Read more
    SDLC Software Development Life Cycle: Analysis → Design → Development → Testing → Deployment → Maintenance Lifecycle → SDLC Phases
    Waterfall Sequential phases, each finished before the next starts Methodologies → Waterfall
    V-Model Waterfall where every phase has a matching test level Methodologies → V-Model
    Agile Mindset of short iterations, working software, and responding to change Methodologies → Agile, Lifecycle → Agile, Scrum, Kanban
    Lean Eliminate waste, optimize the whole flow of value Methodologies → Lean
    Scrum Agile framework of fixed-length sprints with defined roles, events, and artifacts Methodologies → Scrum
    Kanban Continuous flow on a visual board with WIP limits Methodologies → Kanban
    SAFe Scaled Agile Framework: Agile coordinated across many teams Methodologies → SAFe
    PI Program Increment: a SAFe timebox of about 10 weeks (several sprints) that all teams plan and deliver together, kicked off by PI Planning Methodologies → SAFe, Wikipedia: SAFe ↗
    XP Extreme Programming: pairing, TDD, continuous integration, small releases Methodologies → XP
    Shape Up Basecamp's fixed-appetite, six-week cycles with no backlog Methodologies → Shape Up
    RUP Rational Unified Process: iterative phases with formal milestones Methodologies → RUP
    Sprint Fixed timebox (usually 1–4 weeks) that produces a usable increment Lifecycle → Agile, Scrum, Kanban
    Backlog Ordered list of work. The Product Backlog holds everything wanted; the Sprint Backlog holds what this sprint commits to Lifecycle → Agile, Scrum, Kanban, Scrum Guide ↗
    Increment The usable, done work produced in a sprint Lifecycle → Agile, Scrum, Kanban
    Sprint Planning Scrum event at the start of a sprint: pick backlog items and agree the sprint goal Lifecycle → Agile, Scrum, Kanban, Scrum Guide ↗
    Daily Standup / Daily Scrum 15-minute daily sync: progress toward the sprint goal and blockers Lifecycle → Agile, Scrum, Kanban, Scrum Guide ↗
    Sprint Review / Demo Show the increment to stakeholders and adapt the backlog from their feedback Lifecycle → Agile, Scrum, Kanban, Scrum Guide ↗
    Retrospective (Retro) End-of-sprint meeting where the team inspects how it worked (what went well, what didn't) and commits to improvements Lifecycle → Agile, Scrum, Kanban, Methodologies → Scrum, Scrum Guide ↗
    Backlog Refinement (Grooming) Ongoing work to split, clarify, and estimate upcoming backlog items Scrum Guide ↗
    Burndown / Burnup Chart Work remaining / work completed plotted over time in a sprint or release Wikipedia: Burndown chart ↗
    Lead Time / Cycle Time Request → delivered / work started → delivered: the Kanban flow metrics Lifecycle → Agile, Scrum, Kanban, Wikipedia: Lead time ↗
    DORA Metrics Deployment frequency, lead time for changes, change failure rate, time to restore: the four keys of delivery performance DORA: Four keys ↗
    DoD Definition of Done: the shared quality bar every increment must meet Scrum Guide ↗, Atlassian: DoD ↗
    DoR Definition of Ready: what a backlog item needs before a sprint can take it Atlassian: DoR ↗
    WIP Work In Progress, which Kanban limits Methodologies → Kanban
    DevOps Dev and Ops share ownership of building and running software Methodologies → DevOps

    Management & Work Items¶

    Term Meaning Read more
    PO Product Owner: owns the backlog and its priorities Lifecycle → Roles
    SM Scrum Master: facilitates the process and removes blockers Lifecycle → Roles
    PM Product Manager (sometimes Project Manager) Lifecycle → Roles
    BA Business Analyst: turns business needs into specs Lifecycle → Roles
    Tech Lead / Architect Owns technical direction and system design Lifecycle → Roles, Becoming Senior → The Ladder
    Epic Large body of work split into stories, often spanning several sprints Atlassian: Epics, stories, initiatives ↗
    User Story Small requirement from the user's view: As a , I want , so that , with acceptance criteria Lifecycle → SDLC Phases, Atlassian: User stories ↗
    Task / Sub-task Concrete unit of work that is not a story or a bug, such as a chore, config change, or story breakdown Jira: Issue types ↗
    Bug / Defect Behavior that deviates from the spec or from what users expect, filed as a bug report Lifecycle → SDLC Phases, Jira: Issue types ↗
    Ticket / Issue A tracked work item (story, task, bug, …) in a tool like Jira or GitHub Issues Lifecycle → Development Workflow
    CR Change Request: a formal request to change agreed scope, requirements, or a production system, assessed for impact before approval. Also short for Code Review (see Version Control & Review) Wikipedia: Change request ↗
    Spike Time-boxed research task to reduce uncertainty before estimating Wikipedia: Spike ↗
    Story Point Relative estimate of effort, complexity, and uncertainty Atlassian: Estimation ↗
    Velocity Story points a team completes per sprint, used for forecasting rather than as a target Wikipedia: Velocity ↗
    Milestone A checkpoint marking the end of a phase or a key deliverable Methodologies → RUP
    MoSCoW Must / Should / Could / Won't prioritization Wikipedia: MoSCoW ↗
    OKR Objectives and Key Results: goal-setting framework Wikipedia: OKR ↗
    KPI Key Performance Indicator Wikipedia: KPI ↗
    RACI Responsible, Accountable, Consulted, Informed: who does what on a task Wikipedia: RACI ↗
    PMO Project (or Program / Portfolio) Management Office: the group that sets project-management standards, tracks status, budget, and resources across projects, and reports to leadership Wikipedia: PMO ↗
    PMP Project Management Professional, the PMI certification Wikipedia: PMP ↗
    Steering Committee Senior stakeholders who set direction, approve scope and budget, and resolve escalations Wikipedia: Steering committee ↗
    Stakeholder Anyone affected by or with influence over the project Wikipedia: Stakeholder ↗
    Project Charter / Kickoff Document that authorizes the project and its goals / the meeting that starts it Wikipedia: Project charter ↗
    RFP / SOW Request for Proposal (a client asks vendors to bid) / Statement of Work (agreed scope, deliverables, timeline) Wikipedia: RFP ↗, Wikipedia: SOW ↗
    NDA Non-Disclosure Agreement Wikipedia: NDA ↗
    T&M / Fixed Price Contract models: pay for time spent / pay an agreed amount for agreed scope Wikipedia: T&M ↗, Wikipedia: Fixed-price ↗
    WBS Work Breakdown Structure: scope decomposed into deliverables and work packages Wikipedia: WBS ↗
    Gantt Chart / Critical Path Timeline bars of tasks and dependencies / the longest dependent chain, which sets the end date Wikipedia: Gantt chart ↗, Wikipedia: Critical path ↗
    RAID Log Risks, Assumptions, Issues, Dependencies tracked in one register Wikipedia: Risk register ↗
    Scope Creep Uncontrolled growth of scope without matching time or budget; controlled through CRs Wikipedia: Scope creep ↗
    Go-live / Sign-off The moment the system goes to production users / formal acceptance of a deliverable Lifecycle → Environments, Lifecycle → Testing (UAT)
    ROI / TCO Return on Investment / Total Cost of Ownership (build + run + maintain) Wikipedia: ROI ↗, Wikipedia: TCO ↗
    CapEx / OpEx Capital Expenditure (buy assets up front) / Operating Expenditure (pay as you go, e.g. cloud) Wikipedia: CapEx ↗
    POC Proof of Concept: a throwaway build that shows an idea is feasible Wikipedia: Proof of concept ↗
    MVP Minimum Viable Product: smallest product that tests the core hypothesis with real users (also Model-View-Presenter, see Frontend) Wikipedia: MVP ↗

    Requirements & Design¶

    Term Meaning Read more
    BRD Business Requirements Document: what the business needs and why Lifecycle → SDLC Phases
    PRD Product Requirements Document: what the product must do, for whom Wikipedia: PRD ↗
    FR Functional Requirement: what the system does, e.g. "a user can reset their password by email" Lifecycle → Testing, Wikipedia: Functional requirement ↗
    NFR Non-Functional Requirement: how well it does it: performance, security, availability, usability, scalability Lifecycle → Testing, System Design Notes → Types of APIs, Wikipedia: NFR ↗
    FRS Functional Requirements Specification Lifecycle → SDLC Phases
    SRS Software Requirements Specification: functional plus non-functional requirements Lifecycle → SDLC Phases
    Use Case A user goal described as a sequence of interactions with the system Lifecycle → SDLC Phases
    AC Acceptance Criteria: testable conditions that make a story "done" Spec-Driven Development → What the Spec Should Contain
    BD / HLD Basic Design / High-Level Design: components, interfaces, data flow Lifecycle → SDLC Phases
    DD / LLD Detailed Design / Low-Level Design: classes, schemas, algorithms Lifecycle → SDLC Phases, System Design Notes → Design Patterns
    SD System Design: how components, data, and infrastructure fit together at scale Architecture → Building Blocks, System Design Notes
    Design Doc Written proposal for a change: context, options, decision, risks Becoming Senior → Communication
    ADR Architecture Decision Record: a short, immutable note of one decision, its context, and its consequences Becoming Senior → Communication, adr.github.io ↗
    RFC Request for Comments: a proposal circulated for feedback, either an internal design RFC or an IETF standard such as the SSH RFCs System Design Notes → How SSH Works, Wikipedia: RFC ↗
    Spec / SDD Specification / Spec-Driven Development: write the spec first, then generate and verify code against it Spec-Driven Development

    Version Control & Review¶

    Term Meaning Read more
    VCS Version Control System (Git is the standard) Lifecycle → Version Control
    Repository / Clone / Fork A project's tracked history / a local copy of it / your own server-side copy of someone else's repo Git → Daily Workflow, git clone ↗
    Commit / Branch / HEAD A snapshot with a message / a movable pointer to a line of commits / the commit you have checked out Lifecycle → Version Control, git commit ↗
    Working Tree / Staging Area (Index) Your files on disk / the changes selected for the next commit (git add) Pro Git: What is Git? ↗
    Remote / origin / upstream A hosted copy of the repo / the default remote you cloned from / the original repo a fork tracks Git → Three Layers
    Fetch / Pull / Push Download remote changes only / fetch and merge into your branch / upload your commits Git → What git fetch does, git push ↗
    Merge / Rebase Combine branches with a merge commit / replay commits on a new base Git → Merge, Git → Rebase
    Fast-Forward Merge that just moves the branch pointer because there is no divergence git merge ↗
    Squash Fold several commits into one Git → Interactive Rebase
    Interactive Rebase git rebase -i: reorder, squash, edit, or drop commits before sharing them Git → Interactive Rebase
    Cherry-pick Copy one specific commit from another branch onto the current one, e.g. backport a fix to a release branch git cherry-pick ↗
    Revert New commit that undoes an earlier one; safe on shared branches git revert ↗
    Reset Move the branch pointer back (--soft / --mixed / --hard); rewrites history, so use only locally git reset ↗
    Amend git commit --amend: replace the last commit with a fixed version git commit ↗
    Stash Shelve uncommitted changes and restore them later git stash ↗
    Force Push Overwrite the remote branch; prefer --force-with-lease, and never on shared branches git push ↗
    Bisect Binary-search history to find the commit that introduced a bug git bisect ↗
    Blame Show which commit last changed each line git blame ↗
    .gitignore Patterns for files Git should never track gitignore ↗
    Submodule A repo embedded inside another at a pinned commit git submodule ↗
    Conflict Two changes touch the same lines; a human must choose Git → Resolving Conflicts
    Git Flow / GitHub Flow / Trunk-Based Branching models, from heavy to light Lifecycle → Branching Models
    PR / MR Pull Request / Merge Request: a reviewed request to merge one branch into another Code Review → Understanding a PR/MR
    CR Code Review: a second engineer checks a change before merge (also Change Request, see Management & Work Items) Lifecycle → Code Review, How to Review Code
    Diff / Hunk The changes between two versions / one contiguous block of them Code Review → What is a Git Diff?
    Conventional Commits type(scope): subject commit message convention Lifecycle → Conventional Commits
    SemVer Semantic Versioning: MAJOR.MINOR.PATCH Lifecycle → Semantic Versioning
    Release / Tag A versioned, shippable snapshot, marked by a Git tag Lifecycle → Development Workflow
    Changelog Human-readable list of notable changes per version keepachangelog.com ↗
    Monorepo Many projects in one repository Architecture → Code Organization

    Testing & QA¶

    Term Meaning Read more
    QA Quality Assurance: test strategy and verification Lifecycle → Roles
    Test Plan / Test Case / Test Suite The testing strategy and scope / one scenario with steps and an expected result / a group of related cases Lifecycle → SDLC Phases, Wikipedia: Test case ↗
    Testing Pyramid Many unit tests, fewer integration tests, very few E2E tests Lifecycle → Testing, Fowler: Practical Test Pyramid ↗
    Unit Test Tests one function or class in isolation; fast, run on every commit Lifecycle → Testing, Wikipedia: Unit testing ↗
    Integration Test Tests components working together, e.g. a service and its real database Lifecycle → Testing, Wikipedia: Integration testing ↗
    SIT System Integration Testing: the integrated system tested against its external interfaces Wikipedia: System integration testing ↗
    System Test Tests the complete, integrated system against the requirements Lifecycle → Testing, Wikipedia: System testing ↗
    E2E Test End-to-End: drives the whole stack as a user would, e.g. a browser through to the database Lifecycle → Testing, Frontend Toolchain → Testing
    Contract Test Checks that a provider and its consumers still agree on the API shape Fowler: Contract Test ↗
    Functional Test Verifies a functional requirement (FR): does it do the right thing? Lifecycle → Testing
    Non-Functional Test Verifies an NFR: performance, security, usability, reliability Lifecycle → Testing
    Smoke Test Quick, shallow check that the build starts and its critical paths work, run before deeper testing or right after deploy Wikipedia: Smoke testing ↗
    Sanity Test Narrow check that a specific fix or change works, before a full regression run Wikipedia: Sanity check ↗
    Regression Test Re-runs existing tests to make sure a change didn't break old behavior; add one for every fixed bug Wikipedia: Regression testing ↗
    UAT User Acceptance Testing: the business confirms requirements are met and signs off Lifecycle → Testing, Wikipedia: Acceptance testing ↗
    Alpha / Beta Test Pre-release testing by internal users / by a limited group of real users Wikipedia: Alpha and beta testing ↗
    Performance Test Measures speed and resource use (latency, throughput) under a given load Wikipedia: Performance testing ↗
    Load Test Behavior at expected peak load Lifecycle → Testing
    Stress Test Push past capacity to find the breaking point and how the system fails Lifecycle → Testing, Wikipedia: Stress testing ↗
    Spike Test Sudden, sharp jump in load; checks auto-scaling and recovery Wikipedia: Performance testing ↗
    Soak / Endurance Test Normal load held for hours or days to expose leaks and slow degradation Wikipedia: Soak testing ↗
    Security Test / Pentest Probe for vulnerabilities; a penetration test is an authorized simulated attack Security → Common Risks, Wikipedia: Penetration test ↗
    SAST / DAST Static (source code) / Dynamic (running app) Application Security Testing Wikipedia: SAST ↗, Wikipedia: DAST ↗
    Fuzz Test Feed random or malformed input to find crashes and unhandled cases Wikipedia: Fuzzing ↗
    Adversarial Test For LLM and ML systems: deliberately crafted hostile inputs (prompt injection, jailbreaks, perturbed data) that try to make the model misbehave, leak data, or bypass guardrails AI & LLM, Wikipedia: Adversarial ML ↗
    Accessibility Test Checks the UI against WCAG: keyboard use, screen-reader names, contrast Frontend → a11y, W3C: WCAG ↗
    Usability Test Watch real users attempt tasks to find friction Wikipedia: Usability testing ↗
    Compatibility / Cross-Browser Test Same behavior across browsers, devices, and OS versions Frontend Toolchain → Testing, Wikipedia: Compatibility testing ↗
    Snapshot Test Compare output (rendered UI, serialized data) with a stored snapshot Jest: Snapshot testing ↗
    Mutation Test Inject small bugs into the code; good tests should fail (kill the mutant) Wikipedia: Mutation testing ↗
    Property-Based Test Generate many inputs and assert a property that must always hold Wikipedia: Property testing ↗
    Exploratory Test Unscripted testing where a tester learns and designs tests on the fly Wikipedia: Exploratory testing ↗
    Black-Box / White-Box Test Tests from the outside, without seeing the code / tests designed from the code's internals Wikipedia: Black-box ↗, Wikipedia: White-box ↗
    Chaos Test Deliberately inject failures in production-like systems to prove resilience Wikipedia: Chaos engineering ↗
    TDD Test-Driven Development: Red → Green → Refactor Lifecycle → TDD and BDD, Methodologies → TDD
    BDD Behavior-Driven Development: Given / When / Then Methodologies → BDD
    Mock / Stub Test doubles that stand in for real dependencies Frontend Toolchain → Testing, Fowler: Mocks Aren't Stubs ↗
    Fixture Fixed setup state or data a test runs against Wikipedia: Test fixture ↗
    Flaky Test Passes and fails on the same code; usually caused by timing, ordering, or shared state Fowler: Non-Determinism ↗
    Code Coverage Share of code executed by tests Wikipedia: Code coverage ↗

    System Design¶

    Term Meaning Read more
    Latency Time for one request to complete, usually reported as percentiles (p50/p95/p99) Architecture → Performance Bottlenecks, DevOps & SRE → p95/p99
    Throughput Work completed per unit of time (requests/s, MB/s); can rise while latency worsens Architecture → Performance Bottlenecks
    Bandwidth Maximum data rate of a link; throughput is what you actually achieve Wikipedia: Bandwidth ↗
    RPS / QPS / TPS Requests / Queries / Transactions Per Second Wikipedia: Queries per second ↗
    Back-of-the-Envelope Estimation Rough numbers (users → RPS → storage → bandwidth) to size a design before drawing it Wikipedia: Back-of-the-envelope ↗
    Scalability Handle more load by adding resources without a redesign Architecture → Scalability
    Vertical / Horizontal Scaling Scale up (bigger machine) / scale out (more machines behind a load balancer) Architecture → Scalability, Big Data → Scale Up vs Scale Out
    Elasticity / Auto-scaling Add and remove capacity automatically as load changes Wikipedia: Autoscaling ↗
    Stateless / Stateful Service keeps no per-client state between requests (easy to scale out) / it does (needs sticky sessions or shared storage) Architecture → Scalability
    Availability Share of time the system serves requests successfully, measured in nines DevOps & SRE → Nines, Architecture → CAP Theorem
    Reliability The system keeps doing the right thing over time, despite faults Becoming Senior → Reliability
    Durability Once written and acknowledged, data survives crashes Databases → Transactions & ACID, Wikipedia: Durability ↗
    HA High Availability: redundancy plus automatic failover so one failure doesn't cause an outage Wikipedia: High availability ↗
    Fault Tolerance / Redundancy Keep working when parts fail / spare copies of components that make it possible Wikipedia: Fault tolerance ↗
    Failover Switch traffic to a standby when the primary fails Wikipedia: Failover ↗
    SPOF Single Point of Failure: one component whose failure takes the whole system down Architecture → Peer-to-Peer, Wikipedia: SPOF ↗
    DR Disaster Recovery: restore service after losing a site or region, sized by RPO / RTO Becoming Senior → Deployment and Scale, Wikipedia: DR ↗
    LB Load Balancer: spreads traffic across instances (round robin, least connections; L4 or L7) Architecture → Load Balancers
    Reverse Proxy Server in front of your apps that terminates TLS, routes, caches, and hides internals (NGINX, Caddy) Running a Server → The Exposure Chain, Wikipedia: Reverse proxy ↗
    API Gateway Single entry point for clients that handles routing, auth, and rate limiting for many services Architecture → Microservices, microservices.io ↗
    Service Discovery / Service Mesh How services find each other / an infrastructure layer that handles service-to-service traffic, retries, and mTLS microservices.io: Discovery ↗, Wikipedia: Service mesh ↗
    Cache Fast copy of data closer to the reader Architecture → Caching
    Cache-Aside / Write-Through / Write-Behind Caching strategies: app loads on miss / write cache and DB together / write cache now, DB later Architecture → Caching
    TTL / Eviction (LRU) Time To Live before an entry expires / which entry to drop when full (Least Recently Used) Architecture → Caching, Wikipedia: Cache replacement ↗
    CDN Content Delivery Network: edge caches near users Architecture → CDN
    Partitioning / Sharding Split data across nodes by range, hash, or directory Architecture → Partitioning
    Consistent Hashing Hash scheme where adding or removing a node moves only a small share of keys Wikipedia: Consistent hashing ↗
    Hot Spot / Hot Key One shard or key that gets far more traffic than the rest Wikipedia: Shard ↗
    Replication / Read Replica Copies of data on several nodes (leader–follower, multi-leader) / a copy that serves reads Wikipedia: Replication ↗
    Quorum / Leader Election Majority agreement needed for a read or write / choosing one node to coordinate Wikipedia: Quorum ↗, Wikipedia: Leader election ↗
    CAP Consistency, Availability, Partition tolerance: pick two under partition Architecture → CAP Theorem
    PACELC CAP extended: if Partitioned choose A or C, Else choose Latency or Consistency Wikipedia: PACELC ↗
    Strong / Eventual Consistency Every read sees the latest write / replicas converge eventually Databases → Consistency at Scale, Wikipedia: Eventual consistency ↗
    BASE Basically Available, Soft state, Eventually consistent: the opposite trade-off to ACID Databases → Consistency at Scale
    MQ Message Queue: buffers work between producers and consumers (Kafka, RabbitMQ, SQS) Architecture → Message Queues
    Pub/Sub Publishers emit events; every subscriber gets a copy Architecture → Message Queues, System Design Notes → Design Patterns
    Stream Processing Continuous processing of event streams (Kafka Streams, Flink) Architecture → Stream Processing
    Backpressure A slow consumer signals producers to slow down instead of being overwhelmed Wikipedia: Back pressure ↗
    2PC / Saga Two-Phase Commit (atomic commit across nodes) / a chain of local transactions with compensating steps Wikipedia: 2PC ↗, microservices.io: Saga ↗
    CQRS / Event Sourcing Separate write and read models / store state as an append-only log of events Fowler: CQRS ↗, Fowler: Event Sourcing ↗
    Rate Limiting Cap requests per client or key (token bucket, leaky bucket, sliding window) Architecture → Rate Limiting
    Retry / Backoff / Jitter Re-try transient failures with growing, randomized delays Error Handling → Retry with Backoff, System Design Notes → Retry and Resilience
    Circuit Breaker Stop calling a failing dependency for a while Error Handling → Circuit Breaker
    Graceful Degradation Serve a reduced result instead of failing outright Error Handling → Graceful Degradation
    Bottleneck The resource (CPU, memory, I/O, network) that limits the whole system Architecture → Performance Bottlenecks
